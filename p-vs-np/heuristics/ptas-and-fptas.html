PTAS and FPTAS

The last two posts gave fixed guarantees: within 2 for vertex cover, within 1.5 for metric TSP. Those numbers are baked into the algorithms. You can't ask the vertex cover algorithm to try harder and get within 1.1.

For some problems, you can. You pick how accurate you want to be, and there's an algorithm for that accuracy. Want to be within 10%? Fine. Within 1%? Also fine, it just takes longer. Within 0.1%? Longer still, but still polynomial.

These are called approximation schemes, and they're the closest thing NP-Hard problems have to being "nearly easy".

Two Kinds of Scheme​

Write ε\varepsilonε (from Post 64) for how far from optimal you're willing to be. ε=0.01\varepsilon = 0.01ε=0.01 means "within 1%".

PTAS

A Polynomial-Time Approximation Scheme is a family of algorithms, one for every ε>0\varepsilon > 0ε>0, where the algorithm for ε\varepsilonε gets within a factor (1+ε)(1 + \varepsilon)(1+ε) of optimal (or (1−ε)(1 - \varepsilon)(1−ε) for maximisation), and runs in polynomial time for each fixed ε\varepsilonε.

The catch is in "for each fixed ε\varepsilonε". The running time might be something like n1/εn^{1/\varepsilon}n1/ε. For ε=0.5\varepsilon = 0.5ε=0.5 that's n2n^2n2, nice. For ε=0.01\varepsilon = 0.01ε=0.01 that's n100n^{100}n100, which is polynomial but useless.

FPTAS

A Fully Polynomial-Time Approximation Scheme is a PTAS whose running time is polynomial in both nnn and 1ε\frac{1}{\varepsilon}ε1​. Something like n3/εn^3 / \varepsilonn3/ε.

An FPTAS is the best you can hope for with an NP-Hard problem: getting 10 times more accurate costs only about 10 times more work, not an exponent of 10 more.

The Knapsack FPTAS​

Knapsack (Post 21) has an FPTAS, first described by Oscar Ibarra and Chul Kim in 1975. It uses two ideas from earlier posts and joins them with one trick.

  • Idea 1: DP over values
  • Idea 2: Make values small
  • Why little is lost

Post 21 described a dynamic programming algorithm that's fast when the numbers are small. There's a version that builds the table over total value instead of total weight: for each possible total value, what's the lightest set of items that achieves it?

That takes about n×(sum of all values)n \times (\text{sum of all values})n×(sum of all values) steps. Fast if values are small numbers. Slow if they're huge.

So make the values small. Pick a scaling factor

K=ε×(largest value)nK = \frac{\varepsilon \times (\text{largest value})}{n}K=nε×(largest value)​

and replace every value vvv with ⌊v/K⌋\lfloor v / K \rfloor⌊v/K⌋: divide by KKK and throw away the fraction.

New Symbol: ⌊x⌋\lfloor x \rfloor⌊x⌋

"Floor of xxx": round down to the nearest whole number. ⌊3.7⌋=3\lfloor 3.7 \rfloor = 3⌊3.7⌋=3, ⌊5⌋=5\lfloor 5 \rfloor = 5⌊5⌋=5.

Now every value is at most about n/εn / \varepsilonn/ε, so the table is small, and the DP is fast.

Rounding loses at most KKK per item, so at most nK=ε×(largest value)nK = \varepsilon \times (\text{largest value})nK=ε×(largest value) in total across any set of items.

And the optimum is worth at least the largest single value (just take that item alone, assuming it fits). So the loss is at most ε×OPT\varepsilon \times \text{OPT}ε×OPT.

The rounded problem is solved exactly, so its answer, evaluated with the real values, is worth at least (1−ε)×OPT(1 - \varepsilon) \times \text{OPT}(1−ε)×OPT.

The running time works out to about n3/εn^3 / \varepsilonn3/ε. Polynomial in both nnn and 1/ε1/\varepsilon1/ε. That's an FPTAS.

Here it is on ten items. Choose ε\varepsilonε and watch the rounded values, the size of the table, and the value found.

With ε=0.9\varepsilon = 0.9ε=0.9 the values are rounded very coarsely, the table is small, and the answer is a little below the best (about 99% of it). As ε\varepsilonε shrinks, the rounding gets finer and the table grows. The guarantee (shown in the status line) tightens every time.

Notice one thing that confused me for a moment: on this instance, ε=0.1\varepsilon = 0.1ε=0.1 happens to find a slightly worse answer than ε=0.25\varepsilon = 0.25ε=0.25. That's allowed. The guarantee always gets better as ε\varepsilonε shrinks, but on any particular instance, the actual answer can wobble. Usually the real answer is much better than the guarantee anyway.

Why This Doesn't Contradict NP-Hardness​

If we can get within any ε\varepsilonε we like in polynomial time, why not set ε\varepsilonε tiny enough to get the exact answer?

Because "tiny enough" depends on the numbers. To guarantee the exact optimum, ε\varepsilonε has to be smaller than 1 divided by the optimum, so that the allowed error is less than 1. Then 1/ε1/\varepsilon1/ε is about as large as the values themselves, and the running time becomes polynomial in the values, not in their number of digits. That's exactly the pseudo-polynomial algorithm from Post 21 again, and it's exponential in the input length.

So the FPTAS sits right on the boundary: as accurate as you like, but never exactly accurate without paying the exponential price. Post 70 looks at that boundary more closely.

It also explains which problems can have an FPTAS. A problem that stays NP-Hard even when all its numbers are small (called strongly NP-Hard, like bin packing in Post 56 or TSP) can't have an FPTAS unless P=NP\mathcal{P} = \mathcal{NP}P=NP. The rounding trick only works when the hardness lives in the size of the numbers.

A PTAS for TSP on a Map​

Metric TSP can't have a PTAS unless P=NP\mathcal{P} = \mathcal{NP}P=NP; the "within about 1.008 is hard" result from Post 66 rules it out. But if the cities are points on a flat map with straight-line distances (called Euclidean TSP), it can.

In 1996, Sanjeev Arora found a PTAS for Euclidean TSP, and Joseph Mitchell found one independently around the same time. The idea, very roughly, is to divide the map into squares, recursively, and force the tour to cross square boundaries only at a limited number of "portals". Then dynamic programming over the squares finds the best portal-respecting tour, which is provably close to the true best. Arora and Mitchell shared the Gödel Prize in 2010 for this work.

The running time is polynomial for each fixed ε\varepsilonε, but grows very quickly as ε\varepsilonε shrinks, so it's a PTAS, not an FPTAS. In practice, other heuristics are faster. But it settled a big theoretical question: on a flat map, you really can get as close to the best tour as you like.

What We Have Established

A PTAS gets within a factor (1+ε)(1 + \varepsilon)(1+ε) of optimal for any chosen ε>0\varepsilon > 0ε>0, in polynomial time for each fixed ε\varepsilonε (possibly like n1/εn^{1/\varepsilon}n1/ε). An FPTAS is polynomial in both nnn and 1/ε1/\varepsilon1/ε.

Knapsack has an FPTAS (Ibarra and Kim, 1975): scale values down by K=εvmax⁡/nK = \varepsilon v_{\max} / nK=εvmax​/n, round down, and solve the rounded problem exactly by dynamic programming over values. The loss is at most ε×OPT\varepsilon \times \text{OPT}ε×OPT, and the time is about n3/εn^3/\varepsilonn3/ε.

Strongly NP-Hard problems can't have an FPTAS unless P=NP\mathcal{P} = \mathcal{NP}P=NP. Euclidean TSP has a PTAS (Arora; Mitchell; 1996), while general metric TSP doesn't, unless P=NP\mathcal{P} = \mathcal{NP}P=NP.
