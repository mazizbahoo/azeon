EXP: Exponential Time

I've written the word "unknown" a lot in this phase. Is NP=coNP\mathcal{NP} = co\mathcal{NP}NP=coNP? Unknown. Is P=PSPACE\mathcal{P} = \mathcal{PSPACE}P=PSPACE? Unknown. Is factoring in P\mathcal{P}P? Unknown.

After a while it starts to feel like complexity theory is just a list of things nobody can prove. So I want to spend this post on something we can prove. It's one of the few places where the field has a solid, permanent answer, and the technique behind it is going to matter a lot in Phase 4.

The Class​

The Class EXP

EXP\mathcal{EXP}EXP (sometimes written EXPTIME) is the class of yes/no problems that can be solved in time 2p(n)2^{p(n)}2p(n), where p(n)p(n)p(n) is some polynomial in the input size nnn.

So 2n2^n2n, 2n22^{n^2}2n2, 25n32^{5n^3}25n3: all of these count as exponential time.

Just to feel how big that is, here's the calculator from Post 6 again. Slide the input size and watch the 2n2^n2n row run away from everything else.

Everything we've met so far fits inside EXP\mathcal{EXP}EXP:

  • P\mathcal{P}P obviously does. A polynomial is much smaller than an exponential.
  • NP\mathcal{NP}NP does: try all 2p(n)2^{p(n)}2p(n) possible certificates and check each one.
  • PSPACE\mathcal{PSPACE}PSPACE does too, and the reason is worth a section of its own.

Why PSPACE Fits Inside EXP​

This is a counting argument, and I like it because it's simple once you see it.

Think about everything a computer's state includes at one moment: what's written in memory, which instruction it's on, and so on. Call that whole snapshot a configuration.

If the computer is only allowed p(n)p(n)p(n) bits of memory, how many different configurations can it be in? Each bit is 0 or 1, so roughly 2p(n)2^{p(n)}2p(n) possibilities (times a small factor for the current instruction). That's a lot, but it's a fixed, finite number.

Now, a deterministic computer that's going to give an answer can't repeat a configuration. If it ever returned to exactly the same snapshot, it would do exactly the same things again and be stuck in a loop forever. So it must finish within 2p(n)2^{p(n)}2p(n)-ish steps.

Polynomial space means at most exponentially many configurations, which means at most exponential time.

P⊆NP⊆PSPACE⊆EXP\mathcal{P} \subseteq \mathcal{NP} \subseteq \mathcal{PSPACE} \subseteq \mathcal{EXP}P⊆NP⊆PSPACE⊆EXP

The Theorem: More Time Means More Problems​

In 1965, Juris Hartmanis and Richard Stearns proved something that sounds obvious and is actually very hard to make precise:

Time Hierarchy Theorem: with significantly more time, a computer can solve problems that it genuinely could not solve with less.

It's not just "we haven't found a faster algorithm yet". It's a proof that for some problems, no faster algorithm exists. Hartmanis and Stearns later received the Turing Award, computing's highest prize, largely for this work, which helped create complexity theory as a field.

The consequence that matters for us:

P⊊EXP\mathcal{P} \subsetneq \mathcal{EXP}P⊊EXP

There are problems solvable in exponential time that are provably not solvable in polynomial time. Not "probably". Not "nobody has found an algorithm". Provably.

New Symbol: ⊊\subsetneq⊊

"Is a subset of, and not equal to." P⊊EXP\mathcal{P} \subsetneq \mathcal{EXP}P⊊EXP says everything in P\mathcal{P}P is in EXP\mathcal{EXP}EXP, and there's at least one thing in EXP\mathcal{EXP}EXP that isn't in P\mathcal{P}P.

How the Proof Works​

The proof uses a technique called diagonalization, which I'll explain properly in Post 46. Here's the idea in plain words, because it's genuinely clever.

  • 1. List every fast program
  • 2. Build a contrary program
  • 3. Why D is outside P
  • 4. But D is in EXP

Every program can be written as text, and every piece of text can be put in a list, in order of length. So we can imagine a list of every program that runs in polynomial time: program 1, program 2, program 3, and so on.

Now build a new program, DDD. When DDD is given input number iii, it:

  1. Looks up program iii in the list.
  2. Runs program iii on input iii, for a limited (but large) number of steps.
  3. Does the opposite: if program iii said yes, DDD says no. If it said no, DDD says yes.

Could DDD itself be somewhere in the list of polynomial-time programs? Say it's program number kkk.

Then what does DDD do on input kkk? By its own rule, it does the opposite of what program kkk does on input kkk. But program kkk is DDD. So DDD does the opposite of itself. That's impossible.

So DDD isn't in the list. DDD solves a problem that no polynomial-time program solves.

How long does DDD take? It has to simulate other programs for their full polynomial running time, and it has to beat every polynomial, so its own running time has to grow faster than every polynomial. The details are fiddly, but the result is that DDD runs comfortably within exponential time.

So DDD's problem is in EXP\mathcal{EXP}EXP but not in P\mathcal{P}P.

I want to point out something about this proof, because it becomes very important later. DDD is a very artificial problem. Nobody actually wants to solve "do the opposite of program iii on input iii". The proof shows a hard problem exists by building a weird one on purpose. Phase 4 is partly about why this same trick doesn't work for P vs NP.

The Squeeze​

Look at the chain again:

P⊆NP⊆PSPACE⊆EXP\mathcal{P} \subseteq \mathcal{NP} \subseteq \mathcal{PSPACE} \subseteq \mathcal{EXP}P⊆NP⊆PSPACE⊆EXP

We know P≠EXP\mathcal{P} \neq \mathcal{EXP}P=EXP. The two ends of the chain are definitely different. So at least one of the three ⊆\subseteq⊆ signs in between must be a strict "smaller than".

Maybe P≠NP\mathcal{P} \neq \mathcal{NP}P=NP. Maybe NP≠PSPACE\mathcal{NP} \neq \mathcal{PSPACE}NP=PSPACE. Maybe PSPACE≠EXP\mathcal{PSPACE} \neq \mathcal{EXP}PSPACE=EXP. Maybe all three. We know at least one is true.

And we can't prove any particular one of them.

When I first understood this I found it almost funny. It's like knowing for certain that one of three doors is locked, being completely unable to tell which, and having the world's best locksmiths stuck on the same problem for fifty years. Most researchers think all three doors are locked.

Problems That Are Provably Hard​

The artificial problem DDD is not the only thing outside P\mathcal{P}P. Once you have one problem that's provably hard, reductions can spread the hardness to natural problems, exactly like NP-Completeness spread through Phase 2.

A problem is EXP-Complete if it's in EXP\mathcal{EXP}EXP and every EXP\mathcal{EXP}EXP problem reduces to it. And because P≠EXP\mathcal{P} \neq \mathcal{EXP}P=EXP:

The guarantee

Every EXP-Complete problem is provably not in P\mathcal{P}P. Unlike NP-Complete problems, where we only believe there's no fast algorithm, here we know.

A clean example: "Given a program, an input, and a number kkk written in binary, does the program stop within kkk steps?" You can answer it by just running the program for kkk steps. But kkk written in binary has only about log⁡2k\log_2 klog2​k digits, so running for kkk steps is exponential in the input size. This bounded halting problem turns out to be EXP-Complete.

And the most famous examples are games. That's next post.

Where We Stand​

What We Have Established

EXP\mathcal{EXP}EXP is the class of problems solvable in time 2p(n)2^{p(n)}2p(n). It contains P\mathcal{P}P, NP\mathcal{NP}NP and PSPACE\mathcal{PSPACE}PSPACE. PSPACE fits inside because polynomial memory allows only exponentially many configurations.

The Time Hierarchy Theorem (Hartmanis and Stearns, 1965) proves that more time solves strictly more problems, so P⊊EXP\mathcal{P} \subsetneq \mathcal{EXP}P⊊EXP. The proof is a diagonalization: build a program that disagrees with every polynomial-time program.

In the chain P⊆NP⊆PSPACE⊆EXP\mathcal{P} \subseteq \mathcal{NP} \subseteq \mathcal{PSPACE} \subseteq \mathcal{EXP}P⊆NP⊆PSPACE⊆EXP, at least one step is strict, but we can't prove which. EXP-Complete problems are provably not in P\mathcal{P}P.

Up Next​

Post 30 is about chess and Go. When you blow up the board to n×nn \times nn×n, deciding who wins with perfect play is EXP-Complete. That makes them provably harder than anything in P\mathcal{P}P, and almost certainly harder than anything in NP\mathcal{NP}NP.

Which raises an obvious question I had to think about for a while: if chess is provably that hard, how does a computer on my phone beat me every single time?
