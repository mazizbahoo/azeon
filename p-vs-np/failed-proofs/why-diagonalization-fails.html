Why Diagonalization Fails for P vs NP

After writing Post 46, I tried something that I suspect a lot of people try at some point. I sat with a notebook and attempted to diagonalize my way to P≠NP\mathcal{P} \neq \mathcal{NP}P=NP.

The plan felt obvious. List every polynomial-time program. Build a problem that disagrees with program iii on input iii. That problem can't be in P\mathcal{P}P. Now just make sure it's in NP\mathcal{NP}NP, and you're done.

I got stuck on "just make sure it's in NP\mathcal{NP}NP". It took me a while to realise that I'd been stuck in exactly the right place. That step is the whole problem, and there's a theorem explaining why it can't be done with this method alone.

Getting Outside P Is the Easy Part​

Diagonalization is extremely good at one thing: building a problem that isn't in a class.

Post 29 did it. List all polynomial-time programs M1,M2,…M_1, M_2, \ldotsM1​,M2​,…. Define the problem DDD: on input iii, run MiM_iMi​ on input iii and give the opposite answer. DDD disagrees with every polynomial-time program somewhere, so D∉PD \notin \mathcal{P}D∈/P.

New Symbol: ∉\notin∈/

"Is not an element of", or just "is not in". D∉PD \notin \mathcal{P}D∈/P means the problem DDD is not in the class P\mathcal{P}P.

That's not the issue. Getting outside P\mathcal{P}P is the easy half. The question is whether you can get outside P\mathcal{P}P while staying inside NP\mathcal{NP}NP.

Reason 1: Nothing Puts D Inside NP​

Look at what it takes to compute DDD. On input iii, you have to simulate program MiM_iMi​ and flip its answer. Since MiM_iMi​ could be any polynomial-time program, with any polynomial running time, DDD has to be prepared to run longer than every polynomial. That's what puts DDD in EXP\mathcal{EXP}EXP.

For DDD to be in NP\mathcal{NP}NP, every yes-instance would need a short certificate that's quick to check. But what would that certificate be? "Here's proof that MiM_iMi​ rejects input iii" means proving a program doesn't do something, which is a coNPco\mathcal{NP}coNP-style claim, about a computation that might be long.

Nondeterminism helps you find a needle in a haystack. It doesn't help you predict what an arbitrary program will do and then contradict it. Guessing is good for there exists. Diagonalization needs for all: "for every polynomial-time program, this disagrees with it". Those don't fit together in the way the proof needs.

So the diagonal problem lands in EXP\mathcal{EXP}EXP, comfortably outside P\mathcal{P}P, but with no reason at all to be in NP\mathcal{NP}NP.

Reason 2: Relativization​

Suppose someone found a much cleverer diagonal construction, one that somehow did put its problem inside NP\mathcal{NP}NP. Post 37 already explains why it couldn't work.

Diagonalization only uses two facts about programs:

  • they can be listed, and
  • one program can simulate another.

Both facts stay true if every program has the same oracle attached. A program with an oracle can still be written down, and simulating it just means passing along its oracle questions.

So any pure diagonalization argument relativizes. If it proved P≠NP\mathcal{P} \neq \mathcal{NP}P=NP, it would also prove PA≠NPA\mathcal{P}^A \neq \mathcal{NP}^APA=NPA for every oracle AAA. But Baker, Gill and Solovay built an AAA where PA=NPA\mathcal{P}^A = \mathcal{NP}^APA=NPA. So no such argument exists.

Two separate failures

Reason 1 is about this specific construction: the diagonal problem has no reason to be in NP\mathcal{NP}NP.

Reason 2 is about every construction of this kind: any argument that only lists and simulates machines is blocked by relativization.

Reason 2 is the deeper one. It says no amount of cleverness inside the pure diagonal framework will help.

Things Diagonalization Can Still Do​

I don't want to leave the impression that diagonalization is useless for NP\mathcal{NP}NP. It proves some genuinely interesting things, just not the main question.

  • NP has its own hierarchy
  • Ladner's theorem
  • Diagonalization plus something else

There's a version of the Time Hierarchy Theorem for nondeterministic machines, built up in the 1970s and 1980s by Stephen Cook, Joel Seiferas, Michael Fischer, Albert Meyer and Stanislav Žák. It says that nondeterministic machines with more time can solve strictly more problems.

So, for example, there are problems solvable by a nondeterministic machine in n3n^3n3 steps that can't be solved by one in n2n^2n2 steps. Diagonalization can compare nondeterministic with nondeterministic. What it can't do is compare nondeterministic with deterministic.

In 1975, the same year as Baker-Gill-Solovay, Richard Ladner used a clever, "lazy" version of diagonalization to prove:

If P≠NP\mathcal{P} \neq \mathcal{NP}P=NP, then there are problems in NP\mathcal{NP}NP that are neither in P\mathcal{P}P nor NP-Complete.

These are the NP-intermediate problems from Post 27. The construction takes SAT and punches carefully spaced holes in it: long stretches where the problem looks like SAT, alternating with long stretches where it's trivially easy. The holes are placed by diagonalizing against both fast algorithms (so it's not in P\mathcal{P}P) and against reductions from SAT (so it's not NP-Complete).

Notice the "if". Ladner's theorem assumes P≠NP\mathcal{P} \neq \mathcal{NP}P=NP and then uses diagonalization to build something. It doesn't prove the assumption.

The most interesting modern use of diagonalization is in combination with other tools. If you can combine it with some technique that doesn't relativize, the combination doesn't relativize either, so it can sometimes slip past the barriers.

Post 50 describes one result, by Ryan Williams in 2011, that did exactly this: it combined a nondeterministic time hierarchy (diagonalization) with a cleverly designed fast algorithm (which looks inside circuits), and proved a new circuit lower bound that people had been stuck on for years.

What This Taught Me​

Here's how I'd summarise the last two posts, if I had to fit it on a sticky note:

Diagonalization shows a class is missing something. It can't show which class the missing thing lives in.

To separate P\mathcal{P}P from NP\mathcal{NP}NP, you need a problem that's missing from P\mathcal{P}P and present in NP\mathcal{NP}NP. Diagonalization handles the first half and is silent on the second. And because it relativizes, no amount of polishing will make it handle both.

My notebook attempt, by the way, made the exact mistake from Reason 1. I wrote down the diagonal problem, wrote "this is in NP because we can guess...", and then couldn't finish the sentence. At least now I know why.

What We Have Established

Diagonalization easily builds problems outside P\mathcal{P}P, but the diagonal problem needs to simulate and contradict every polynomial-time program, which puts it in EXP\mathcal{EXP}EXP with no reason to be in NP\mathcal{NP}NP: nondeterminism handles "there exists", not "for all programs".

More fundamentally, pure diagonalization only lists and simulates machines, so it relativizes, and Baker-Gill-Solovay shows relativizing arguments can't settle P vs NP.

Diagonalization still proves the nondeterministic time hierarchy and Ladner's theorem (if P≠NP\mathcal{P} \neq \mathcal{NP}P=NP, NP-intermediate problems exist), and combined with non-relativizing tools it can still produce new results.
