Hash Functions & Passwords

When I first made accounts on websites as a kid, I assumed the website kept a list of everyone's passwords, and when you logged in it checked whether what you typed matched what was on the list.

That would be a terrible design. If anyone ever stole that list, every single account would be exposed at once, and since people reuse passwords, many of their other accounts too.

A well-built system never stores your password at all. It stores a fingerprint of it. This post explains how that works, how it connects to P vs NP, and corrects the way I originally planned to describe it.

What a Hash Function Is​

A hash function takes any input (a password, a file, a whole book) and produces a fixed-size output, called a hash or digest. One of the most widely used today is SHA-256, which always produces 256 bits, usually written as 64 hexadecimal characters.

A cryptographic hash function is designed to have a few properties:

PropertyMeaning
DeterministicThe same input always gives the same hash
Fast to computeHashing is quick, even for big inputs
One-way (preimage resistant)Given a hash, it's infeasible to find any input that produces it
Collision resistantIt's infeasible to find two different inputs with the same hash
Avalanche effectChanging the input even slightly changes the hash completely

Here's real SHA-256, computed in your browser. Change one character of either input and watch about half of the 256 bits flip.

"password123" and "password124" differ in one character. Their hashes look completely unrelated. That's the avalanche effect, and it means a hash gives an attacker no clue about which inputs are "close" to the right one.

How Passwords Are Stored​

  • Sign up
  • Log in
  • Why the salt?

When you create an account, the server generates a random string called a salt, combines it with your password, hashes the result, and stores the salt and the hash. It throws your actual password away.

When you log in, the server takes what you typed, combines it with your stored salt, hashes it the same way, and compares the result with the stored hash. Same hash means same password, so you're in.

The server checks your password without ever storing it.

Without salts, everyone with the password "password123" would have the same hash. An attacker could precompute the hashes of millions of common passwords once (these lists are called rainbow tables) and look up stolen hashes instantly.

With a random salt per user, the same password gives a different hash for every user, so precomputed tables are useless, and each account has to be attacked separately.

Modern systems go one step further: they use hash functions that are deliberately slow, like bcrypt (1999), scrypt (2009) or Argon2 (which won the Password Hashing Competition in 2015). Logging in once takes a fraction of a second, which you don't notice. But an attacker trying billions of guesses has to pay that cost billions of times.

This matters in practice. When LinkedIn was breached in 2012, its passwords had been stored as plain SHA-1 hashes with no salt, and a huge fraction of them were cracked and published.

Where P vs NP Comes In​

Here's the connection, and it's the same shape as Post 52.

Reversing a hash is an NP\mathcal{NP}NP-style search. Given a hash hhh, find an input xxx with hash(x)=h\text{hash}(x) = hhash(x)=h. If someone hands you a candidate xxx, you check it by hashing once. Fast. So finding preimages is the kind of problem that P=NP\mathcal{P} = \mathcal{NP}P=NP would make easy.

So, if P=NP\mathcal{P} = \mathcal{NP}P=NP in a practical way, no hash function could be truly one-way, and password hashes would protect nothing.

That's why the security of stored passwords depends on P≠NP\mathcal{P} \neq \mathcal{NP}P=NP.

The Correction: It's Not NP-Hardness​

My original plan for this post said "NP-hardness protects user databases". When I started writing it, I realised that's not right, and the reason is important.

  • Hashes aren't NP-Hard to invert
  • What actually protects you

Nobody has shown that reversing SHA-256, or any practical hash function, is NP-Hard. And for good reason: NP-Hardness is about the worst case, while a hash needs to be hard to reverse on typical outputs. Being NP-Hard would guarantee hardness only for some unlucky inputs, not for your password.

There's even research suggesting it's difficult to base one-way functions on NP-Hardness in the most natural ways. So cryptographers don't try. Hash functions are designed to be hard on average, then attacked relentlessly by experts, and trusted only after surviving years of that.

What protects you is a combination of:

  1. The hash function being one-way in practice: decades of failed attempts to reverse it.
  2. Salts, so attacks can't be shared between accounts.
  3. Slowness, so each guess is expensive.
  4. Your password being hard to guess. This one matters most.

That last point is uncomfortable. If your password is "password123", no hash function in the world helps much. The attacker doesn't reverse the hash. They just guess common passwords, hash each guess, and compare. That's checking certificates, which is the easy direction.

So the honest picture is: password security needs P≠NP\mathcal{P} \neq \mathcal{NP}P=NP, but it rests on stronger, unproven assumptions about specific hash functions, and on users choosing passwords that aren't on a list of common guesses.

Hashes That Got Broken​

It's worth knowing that hash functions do get broken, though not by solving P vs NP. They get broken because someone finds a weakness in their specific design.

  • MD5 was once widely used. In 2004, Xiaoyun Wang and colleagues showed how to find collisions in it quickly. It's now considered broken for security purposes.
  • SHA-1 followed. In 2017, researchers from Google and CWI Amsterdam published the first practical collision: two different PDF files with the same SHA-1 hash.

In both cases, the problems found were collisions, not full reversals. But they show the pattern from Post 21 again: hardness of a general problem tells you nothing about a specific design. What keeps SHA-256 trusted today is that nobody has found a weakness despite years of effort.

What We Have Established

A cryptographic hash function maps any input to a fixed-size fingerprint that's fast to compute, believed infeasible to reverse, collision resistant, and changes completely when the input changes slightly. Websites store salted hashes, ideally with deliberately slow functions like bcrypt, scrypt or Argon2, so a stolen database doesn't reveal passwords directly.

Reversing a hash is an NP\mathcal{NP}NP-style search, so P=NP\mathcal{P} = \mathcal{NP}P=NP would break hash-based protection. But hash functions are not NP-Hard to invert, and their security rests on stronger, typical-case assumptions tested by years of attacks. MD5 and SHA-1 were broken by design flaws, not by any progress on P vs NP.
